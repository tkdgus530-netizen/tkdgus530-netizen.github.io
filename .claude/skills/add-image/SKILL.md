# 이미지 추가 (images/ + data/site.json)

## 1단계: 이미지부터 받는다

스킬이 호출되면 **다른 작업보다 먼저 이미지 파일을 받는다.**

- 호출 메시지에 파일 경로가 없으면 이렇게만 묻고 기다린다: "올릴 이미지 파일을 알려 주세요. 파일을 터미널 창에 끌어다 놓으면 경로가 들어갑니다. 여러 장이면 한 번에 넣어 주세요."
- 받은 파일마다 실제로 있는지, 이미지인지 확인하고 목록으로 보여 준다:
  ```bash
  for f in "경로1" "경로2"; do ls -lh "$f" && sips -g pixelWidth -g pixelHeight "$f" | tail -2; done
  ```
- 없는 파일·이미지가 아닌 파일이 있으면 그 파일만 다시 받는다. **모든 파일이 확인되기 전에는 2단계로 넘어가지 않는다.**

## 2단계: 한 후기에 넣는 게 맞는지 확인한다

**스킬 한 번 호출에 후기는 하나만 등록한다.** 받은 이미지 목록을 보여 주며 묻는다: "이 N장을 **후기 한 개**에 모두 넣으려는 게 맞나요?"

| 답 | 다음 |
|---|---|
| 예 | 3단계로. |
| 아니오 — 여러 후기에 나눠 넣으려 함 | 이번 후기에 넣을 이미지만 고르게 하고, 나머지는 후기마다 스킬을 다시 불러 등록하라고 안내한다. 한 번에 여러 후기를 만들지 않는다. |
| 아니오 — 앨범·프로필 사진 | 후기 단계(3단계)를 건너뛰고 아래 표의 해당 위치에 넣는다. |

사용자가 처음부터 "이 3장 한 후기로 올려줘"처럼 분명히 말했어도 목록을 보여 주고 확인은 받는다.

## 3단계: 후기 정보를 차례대로 받는다

**질문 하나에 값 하나만 받는다.** 아래 6개를 순서대로 하나씩 묻고, 그 값이 채워진 뒤에야 다음 질문을 한다. 두 값 이상을 한 질문에 묶지 않는다.

**빠지거나 모호한 답은 반드시 되묻는다.** 비워 두거나 추측해 채우지 않고, 같은 질문을 구체적으로 다시 해서 그 값을 채운다. 한 답에 다음 질문의 값까지 들어 있어도(예: 년도 질문에 "2026년 5월") 미리 채우지 말고, 다음 차례에 "5월이 맞나요?"로 확인받는다.

| 순서 | 질문 | 들어갈 곳 | 규칙 |
|---|---|---|---|
| 1 | "후기 글을 보내 주세요. 이미지에 글이 다 담겨 있어 따로 쓸 글이 없으면 '없음'이라고 해 주세요." | `text` | 받은 문장 그대로, 맞춤법만 고친다. 줄바꿈은 `\n`. 사용자가 직접 '없음'이라고 답한 경우에만 `""`. |
| 2 | "예식 년도를 알려 주세요. 예: 2026" | `year` | 필수. 4자리 문자열 `"2026"`. "작년"처럼 모호하면 숫자로 다시 묻는다. |
| 3 | "몇 월이었나요? 예: 5" | `month` | 필수. 1~12, 앞자리 0 없는 문자열 `"5"`. "봄"처럼 모호하면 숫자로 다시 묻는다. |
| 4 | "의뢰인의 성을 알려 주세요. 예: 김" | `author` 앞부분 | 필수. 성 한 글자(또는 두 글자 성)만 받는다. 이름까지 받으면 성만 쓰고 나머지는 `○○`로 가린다고 알린다. |
| 5 | "신부님과 신랑님 중 어느 쪽으로 표시할까요?" | `author` 뒷부분 | 필수. 답이 '신부'·'신랑'이 아니면 다시 묻는다. 4·5를 합쳐 `"김○○ 신부님"`으로 저장한다. |
| 6 | "예식장이나 예식 형태를 알려 주세요. 예: 더채플 강남, 야외 웨딩. 적지 않으려면 '없음'이라고 해 주세요." | `meta` | 날짜는 넣지 않는다. 사용자가 직접 '없음'이라고 답한 경우에만 `""`. |

모든 값이 채워지면 등록될 후기를 한 번 보여 주고 확인받은 뒤 4단계로 간다:

```json
{ "text": "...", "author": "김○○ 신부님", "year": "2026", "month": "5", "meta": "더채플 강남", "image": "", "images": ["images/20261020_review-202605-kim-bride_image_1.jpg", "images/20261020_review-202605-kim-bride_image_2.jpg"] }
```

새 후기는 `reviews.items` **맨 앞**에 넣는다(최신순).

## 어디에 들어가나

| 용도 | site.json 위치 |
|---|---|
| 후기 이미지 | 새 후기의 `"images": ["images/20261020_review-202605-kim-bride_image_1.jpg", "images/20261020_review-202605-kim-bride_image_2.jpg"]` |
| 앨범 | `album.items` 맨 앞에 `{ "src": "images/20261020_album_image_1.jpg", "caption": "2026년 5월 · 야외 웨딩" }` |
| 프로필 | `hero.photo` |

- 후기 이미지는 장 수와 관계없이 **`images` 배열**에 받은 순서대로 넣고 `"image"`는 `""`로 둔다. 화면은 한 장이면 크게, 여러 장이면 2열로 보여 준다.
- 경로는 반드시 `images/...`. `./images/...`, `/images/...`, 절대경로는 화면 코드가 버린다.
- 앨범 `caption`은 방문자에게 보이므로 신랑·신부 이름을 넣지 않는다.

## 파일 이름 규칙: `yyyyMMdd_<대상>_image_N.확장자`

이미지가 겹치지 않고, 이름만 보고도 **어느 후기의 이미지인지** 알 수 있도록 모든 이미지를 이 이름으로 바꿔서 넣는다. 원본 파일 이름은 쓰지 않는다.

| 부분 | 규칙 |
|---|---|
| `yyyyMMdd` | 이미지를 등록하는 **오늘 날짜**(`date +%Y%m%d`). 예식 날짜가 아니다. |
| `<대상>` | 후기: `review-<예식 yyyyMM>-<성 로마자>-<bride\|groom>` — 3단계에서 받은 년도·월(월은 두 자리로 채움)·성·호칭으로 만든다. 앨범: `album`. 프로필: `profile`. |
| `N` | 같은 `yyyyMMdd_<대상>_image_` 이름이 이미 있으면 그 최댓값 + 1부터, 없으면 1부터. 받은 순서대로 1씩 올린다. 0 채움 없음. |
| 확장자 | 저장되는 형식 그대로 소문자. JPEG로 줄이면 `.jpg`(원본이 `.heic`·`.jpeg`·`.JPG`여도), 투명 PNG를 유지하면 `.png`. |

예: 2026년 5월 김○○ 신부님 후기에 2장 → `20261020_review-202605-kim-bride_image_1.jpg`, `20261020_review-202605-kim-bride_image_2.jpg`

**성 로마자** (파일 이름은 영문 소문자만 쓴다. 한글 파일 이름은 macOS에서 자모가 분리돼 site.json 경로와 안 맞을 수 있다):

김 kim · 이 lee · 박 park · 최 choi · 정 jung · 강 kang · 조 cho · 윤 yoon · 장 jang · 임 lim · 한 han · 오 oh · 서 seo · 신 shin · 권 kwon · 황 hwang · 안 ahn · 송 song · 전 jeon · 홍 hong · 유 yoo · 류 ryu · 고 ko · 문 moon · 양 yang · 손 son · 배 bae · 백 baek · 허 heo · 남 nam · 심 shim · 노 noh · 하 ha · 곽 kwak · 성 sung · 차 cha · 주 joo · 우 woo · 구 koo · 민 min · 진 jin · 나 na · 지 ji · 엄 eom · 채 chae · 원 won · 천 chun · 방 bang · 공 kong · 현 hyun · 함 ham · 변 byun · 염 yeom · 여 yeo · 추 choo · 도 do · 소 so · 석 seok · 선 sun · 설 seol · 마 ma · 길 gil · 연 yeon · 위 wi · 표 pyo · 명 myung · 기 ki · 반 ban · 왕 wang · 금 keum · 옥 ok · 육 yook · 인 in · 맹 maeng · 제 je · 모 mo · 탁 tak · 국 kook · 어 eo · 은 eun · 편 pyun · 용 yong · 예 ye · 경 kyung · 봉 bong · 사 sa · 부 boo · 황보 hwangbo · 남궁 namgung · 제갈 jegal · 선우 sunwoo · 독고 dokgo · 사공 sagong

표에 없는 성이면 추측하지 말고 "파일 이름에 쓸 영문 성을 알려 주세요. 예: kim"이라고 묻는다.

다음 번호 구하기 (`T`에 대상을 넣는다):
```bash
D=$(date +%Y%m%d); T=review-202605-kim-bride
N=$(( $(ls images 2>/dev/null | sed -n "s/^${D}_${T}_image_\([0-9]*\)\..*/\1/p" | sort -n | tail -1) + 1 )); echo "${D}_${T}_image_${N}"
```

저장하기 전에 "원본 이름 → 새 이름" 목록을 사용자에게 보여 준다. 예: `IMG_1234.HEIC → 20261020_review-202605-kim-bride_image_1.jpg`

## 4단계: 넣기

1. 원본은 그대로 두고, 긴 변 1800px JPEG로 줄여 `images/`에 저장:
   ```bash
   sips -s format jpeg -s formatOptions 82 -Z 1800 "원본.heic" --out images/20261020_review-202605-kim-bride_image_1.jpg
   ```
   투명 배경 PNG(로고 등)만 형식을 유지하고 `-Z 1800`.
2. `data/site.json` 수정(들여쓰기 2칸, 한글 그대로).
3. 프로필을 바꿨다면 `index.html` 맨 위 `og:image`도 `https://tkdgus530-netizen.github.io/images/...`로 맞춘다.
4. 확인:
   ```bash
   python3 -c "
   import json,os;d=json.load(open('data/site.json'))
   ps=[d['hero']['photo']]+[a['src'] for a in d['album']['items']]
   for r in d['reviews']['items']: ps+= [r.get('image','')]+r.get('images',[])
   bad=[p for p in ps if p and (not p.startswith('images/') or not os.path.exists(p))];print('문제:',bad or '없음')"
   ls -lh images
   ```
   한 장이 1MB를 크게 넘으면 `formatOptions`를 낮춘다.
5. 등록된 후기와 이미지 장 수를 보여 주고 **마지막 단계**로 간다.

## 삭제·교체

- 삭제: site.json에서 경로를 지우고, 다른 곳에서 안 쓰면(`grep -n 파일이름 data/site.json index.html`) 파일도 지운다.
- 교체: 기존 파일을 덮어쓰지 않는다(캐시 때문에 옛 사진이 보일 수 있음). 새 사진을 이름 규칙대로 새 번호로 넣고 경로를 바꾼다.

## 마지막 단계: 바뀐 내용 보여 주기 → 반영(푸시)은 요청받았을 때만

### 1. `git diff`로 변경 전·후를 보여 준다

파일을 고쳤으면 **항상** 실행한다:

```bash
git status --short -- data/ images/ index.html
git diff -- data/site.json index.html
```

- diff 원문을 그대로 붙이지 말고, 바뀐 곳마다 **변경 전 → 변경 후** 표로 정리한다. `-` 줄이 변경 전, `+` 줄이 변경 후다.

  | 위치 | 변경 전 | 변경 후 |
  |---|---|---|
  | `reviews.items[0]` | (없음) | 김○○ 신부님 · 2026년 5월 · "사회 덕분에…" |
  | `services.items[0].title` | 일반 사회 · 200,000원 | 일반 사회 · 220,000원 |

- 새로 넣은 파일(`??`)과 지운 파일(` D`)은 diff에 내용이 안 나오므로 status 결과로 따로 적는다.
- 이번 작업에서 고치지 않은 변경이 diff에 섞여 있으면 "이번 작업과 무관한 변경"으로 구분해 알린다.
- 끝에 한 줄 덧붙인다: "공개 사이트에 반영하려면 '반영해줘'라고 말씀해 주세요."

### 2. 커밋·푸시는 사용자가 직접 요청할 때만, 그리고 한 번 더 묻는다

- 사용자가 "반영해줘", "푸시해줘", "공개 사이트에 올려줘"처럼 **공개 사이트 반영을 직접** 말하기 전에는 커밋도 푸시도 하지 않는다. "좋아요", "확인했어요", "고마워요"는 반영 요청이 아니고, 스킬을 부를 때의 "후기 올려줘"·"사진 올려줘"도 파일을 고쳐 달라는 뜻일 뿐 푸시 요청이 아니다.
- 요청을 받아도 바로 하지 않고 **한 번 더 묻는다**:

  ```
  아래 내용으로 공개 사이트에 반영(푸시)할까요? 푸시하면 1~2분 뒤 누구나 볼 수 있습니다.
  - 올릴 파일: data/site.json, images/20261020_review-202605-kim-bride_image_1.jpg
  - 커밋 메시지: 후기 추가: 김○○ 신부님 (2026년 5월)
  '예'라고 답해 주시면 진행합니다.
  ```

- '예', '네 올려줘'처럼 분명히 승낙한 경우에만 3으로 간다. 답이 애매하거나 고칠 곳을 말하면 푸시하지 않고, 고친 뒤 1부터 다시 한다.

### 3. 반영

1. 이번 작업에서 바꾼 파일만 이름을 적어 `git add` 한다(`git add -A`, `git add .` 금지). 내용 파일(`data/`, `images/`)과 그 밖의 파일(`index.html` 등)은 커밋을 나눈다.
2. 커밋 메시지는 한국어로, 첫 줄에 무엇을 바꿨는지 쓴다.
3. 푸시 바로 전에 `git pull --rebase origin main`. 충돌이 나면 `git rebase --abort` 하고 푸시하지 않은 채 알린다. 커밋하지 않은 다른 변경 때문에 pull이 거부되면 stash 하지 말고 멈춰서 알린다.
4. `git push origin main`. `--force`는 쓰지 않는다.
5. 푸시한 커밋(해시·메시지)을 보여 주고, 1~2분 뒤 공개 사이트에 반영된다고 알린다.

## 흔한 실수

- 이미지를 받기 전에 site.json부터 열어 대상을 고름.
- 여러 장을 받고 확인 없이 한 후기에 다 넣거나, 앨범에 넣음.
- 한 번 호출에 후기를 두 개 이상 만듦.
- 한 질문에 두 값 이상을 묶어 물음(예: "년도와 월을 알려 주세요").
- 한 답에 들어 있던 다음 값을 확인 없이 미리 채움.
- 빠지거나 모호한 답을 되묻지 않고 `""`로 비우거나 추측해 채움.
- 후기에 `image`와 `images`를 둘 다 채워 같은 사진이 두 번 보임.
- 휴대폰 원본(4~10MB)을 그대로 올림.
- 원본 파일 이름(`IMG_1234.HEIC`, `카톡 캡처.png`)을 그대로 쓰거나, 번호를 1부터 다시 매겨 같은 날 올린 이미지를 덮어씀.
- 확장자를 원본(`.heic`)대로 두고 내용은 JPEG로 저장함.
- 사용자가 반영을 직접 요청하지 않았는데 커밋·푸시함. 요청을 받고도 한 번 더 묻지 않고 바로 푸시함.
- `git diff`로 변경 전·후를 보여 주지 않고 "고쳤습니다"로만 끝냄.
