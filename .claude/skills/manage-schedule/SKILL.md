# 예식 일정 관리 (data/site.json → schedule.items)

## 일정 한 건의 모양

```json
{ "date": "2026-11-07", "start": "11:00", "end": "12:30", "area": "서울 강남" }
```

| 필드 | 규칙 |
|---|---|
| `date` | `YYYY-MM-DD`, 0 채움. "11월 7일"처럼 연도가 없으면 오늘 기준 다가오는 날짜로 보고, 그렇게 해석했다고 말한다. |
| `start`, `end` | 24시간 `HH:MM`, 0 채움(`9:00` ✗ → `09:00`). "오후 2시" → `14:00`. `end`를 모르면 `""` → 1시간으로 계산됨. |
| `area` | 방문자에게 그대로 보인다. **넓은 지역만**(`서울 강남`, `경기 수원`). 예식장 상호·신랑신부 이름·연락처는 넣지 않는다. 사용자가 예식장 이름을 주면 지역으로 바꿔 넣고 알린다. |

하루 기준은 09:00~21:00이고, 이 안에 60분 이상 빈 시간이 없으면 달력에 **마감**으로 표시된다. 화면이 날짜·시간순으로 정렬하지만, 파일도 **날짜→시작시간 순**으로 정렬해 둔다.

## 절차

1. `git pull --rebase origin main`.
2. **추가**: 같은 날 기존 일정과 시간이 겹치면(종료 없는 건 1시간으로 계산) 넣기 전에 사용자에게 알리고 확인받는다.
3. **수정·삭제**: `date`(+`start`)로 대상을 찾는다. 그날 일정이 여러 개면 목록을 보여 주고 어느 것인지 확인한다. 지나간 일정 정리를 부탁받으면 오늘 이전 항목만 지운다.
4. 정렬 후 저장(들여쓰기 2칸, 한글 그대로).
5. 확인 — 형식 오류·겹침·마감 날짜를 출력:
   ```bash
   python3 - <<'EOF'
   import json,re
   d=json.load(open('data/site.json'));it=d['schedule']['items']
   m=lambda t:int(t[:2])*60+int(t[3:])
   ok=lambda t:bool(re.fullmatch(r'([01]\d|2[0-3]):[0-5]\d',t))
   by={}
   for x in it:
       assert re.fullmatch(r'\d{4}-\d{2}-\d{2}',x['date']) and ok(x['start']) and (x['end']=='' or ok(x['end'])),x
       s=m(x['start']);e=m(x['end']) if x['end'] and m(x['end'])>s else s+60
       by.setdefault(x['date'],[]).append((s,e,x))
   for day,b in sorted(by.items()):
       b.sort();cur=540;free=[]
       for s,e,_ in b:
           if s>cur:free.append(min(s,1260)-cur)
           cur=max(cur,e)
       if cur<1260:free.append(1260-cur)
       over=[(a[2]['start'],c[2]['start']) for a,c in zip(b,b[1:]) if c[0]<a[1]]
       print(day,[x['start']+'~'+(x['end'] or '?')+' '+x['area'] for *_,x in b],'겹침'+str(over) if over else '','마감' if not any(f>=60 for f in free) else '')
   print('정렬됨' if it==sorted(it,key=lambda x:(x['date'],x['start'])) else '정렬 필요')
   EOF
   ```
6. 바뀐 일정을 사용자에게 보여 주고(마감으로 바뀐 날짜가 있으면 함께) **마지막 단계**로 간다.

## 마지막 단계: 바뀐 내용 보여 주기 → 반영(푸시)은 요청받았을 때만

### 1. `git diff`로 변경 전·후를 보여 준다

파일을 고쳤으면 **항상** 실행한다:

```bash
git status --short -- data/ images/ index.html
git diff -- data/site.json index.html
```

- diff 원문을 그대로 붙이지 말고, 바뀐 곳마다 **변경 전 → 변경 후** 표로 정리한다. `-` 줄이 변경 전, `+` 줄이 변경 후다.

  | 위치 | 변경 전 | 변경 후 |
  |---|---|---|
  | `reviews.items[0]` | (없음) | 김○○ 신부님 · 2026년 5월 · "사회 덕분에…" |
  | `services.items[0].title` | 일반 사회 · 200,000원 | 일반 사회 · 220,000원 |

- 새로 넣은 파일(`??`)과 지운 파일(` D`)은 diff에 내용이 안 나오므로 status 결과로 따로 적는다.
- 이번 작업에서 고치지 않은 변경이 diff에 섞여 있으면 "이번 작업과 무관한 변경"으로 구분해 알린다.
- 끝에 한 줄 덧붙인다: "공개 사이트에 반영하려면 '반영해줘'라고 말씀해 주세요."

### 2. 커밋·푸시는 사용자가 직접 요청할 때만, 그리고 한 번 더 묻는다

- 사용자가 "반영해줘", "푸시해줘", "공개 사이트에 올려줘"처럼 **공개 사이트 반영을 직접** 말하기 전에는 커밋도 푸시도 하지 않는다. "좋아요", "확인했어요", "고마워요"는 반영 요청이 아니고, 스킬을 부를 때의 "후기 올려줘"·"사진 올려줘"도 파일을 고쳐 달라는 뜻일 뿐 푸시 요청이 아니다.
- 요청을 받아도 바로 하지 않고 **한 번 더 묻는다**:

  ```
  아래 내용으로 공개 사이트에 반영(푸시)할까요? 푸시하면 1~2분 뒤 누구나 볼 수 있습니다.
  - 올릴 파일: data/site.json, images/20261020_review-202605-kim-bride_image_1.jpg
  - 커밋 메시지: 후기 추가: 김○○ 신부님 (2026년 5월)
  '예'라고 답해 주시면 진행합니다.
  ```

- '예', '네 올려줘'처럼 분명히 승낙한 경우에만 3으로 간다. 답이 애매하거나 고칠 곳을 말하면 푸시하지 않고, 고친 뒤 1부터 다시 한다.

### 3. 반영

1. 이번 작업에서 바꾼 파일만 이름을 적어 `git add` 한다(`git add -A`, `git add .` 금지). 내용 파일(`data/`, `images/`)과 그 밖의 파일(`index.html` 등)은 커밋을 나눈다.
2. 커밋 메시지는 한국어로, 첫 줄에 무엇을 바꿨는지 쓴다.
3. 푸시 바로 전에 `git pull --rebase origin main`. 충돌이 나면 `git rebase --abort` 하고 푸시하지 않은 채 알린다. 커밋하지 않은 다른 변경 때문에 pull이 거부되면 stash 하지 말고 멈춰서 알린다.
4. `git push origin main`. `--force`는 쓰지 않는다.
5. 푸시한 커밋(해시·메시지)을 보여 주고, 1~2분 뒤 공개 사이트에 반영된다고 알린다.

## 꼭 알릴 것

**아티팩트의 '공개 사이트에 반영'은 `data/site.json`을 통째로 덮어쓴다.** 여기서 바꾼 일정은 아티팩트에도 똑같이 반영하지 않으면 다음 반영 때 되돌아간다. 끝날 때 한 줄로 알린다.

## 흔한 실수

- `9:00`, `2026-11-7`처럼 0을 빼먹음 → 달력 계산에서 빠짐.
- `end`가 `start`보다 빠름(자정 넘김 등) → 1시간짜리로 계산됨. 사용자에게 확인.
- `area`에 "홍길동♥김영희 더채플" 같은 개인 정보.
- 연도 없는 날짜를 올해로 단정해 이미 지난 날짜에 넣음.
- 사용자가 반영을 직접 요청하지 않았는데 커밋·푸시함. 요청을 받고도 한 번 더 묻지 않고 바로 푸시함.
- `git diff`로 변경 전·후를 보여 주지 않고 "고쳤습니다"로만 끝냄.
